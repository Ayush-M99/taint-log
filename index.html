Three gaps in Semgrep's MCP security rules

Drafted by Claude, including the rule reading, the test cases and the patch. Approved for publication by Ayush-M99. Filed as semgrep-rules #4127, with the fix in PR #4128.

MCP servers expose functions to AI agents, and the agent fills in the arguments. Text that reaches a tool parameter may come from a web page or file the agent read, so a parameter passed to a shell is a command injection risk. Semgrep ships rules for this, and we tested how much they catch.

Gap 1: the decorator has to be empty

mcp-command-injection-python marks tool parameters as untrusted, but its pattern only matches the decorator with empty parentheses. Add a description and the parameter is no longer tracked.

@mcp.tool()                          # flagged
def ping(host: str) -> int:
    return os.system("ping " + host)

@mcp.tool(description="Ping a host") # missed
def ping(host: str) -> int:
    return os.system("ping " + host)

The rule's test file only uses the empty form, so its tests could not show this. The fix is one token: @$SERVER.tool(...). Three more rules share the gap: mcp-ssrf-python, mcp-unsanitized-return-python and mcp-credential-in-response-python. Each flagged the empty form and missed the form with arguments, and each flagged both after the same one-token change. A sibling rule, mcp-typosquatted-tool-name-python, already handles arguments.

Gap 2: a short list of shell sinks

The rule lists os.system, eval, exec, and subprocess.run, call and Popen. Everyday alternatives such as os.popen, subprocess.check_output and subprocess.getoutput pass silently.

Gap 3: nothing may follow shell=True

llm-output-to-exec-python flags model output that reaches a shell. Its patterns end at shell=True, so one more keyword after it hides the call. Argument order alone decides the result.

subprocess.run(cmd, shell=True)                       # flagged
subprocess.run(cmd, capture_output=True, shell=True)  # flagged
subprocess.run(cmd, shell=True, capture_output=True)  # missed

Results

RuleUnsafe flagged, currentUnsafe flagged, patchedSafe flagged, patched
mcp-command-injection-python2 of 910 of 100 of 7

The patched runs each include one extra unsafe case. The safe cases include list arguments, shlex.quote, calls with no shell=True, and functions with other decorators.

We then ran both patched rules against their extended test files, using the playground's ruleid and ok assertions. All passed: 16 of 16 for the MCP rule and 13 of 13 for the LLM rule.

Limits of this test

  • These are cases we wrote to probe the gaps, so the percentages say nothing about real-world detection rates.
  • We ran the rules in the Semgrep playground, with message and metadata omitted. A semgrep test run on a checkout is still to do.
  • The three test cases added for mcp-ssrf-python, mcp-unsanitized-return-python and mcp-credential-in-response-python have not been run as written.
  • For mcp-ssrf-python and mcp-unsanitized-return-python we tested reduced rules that use only requests.get.

Benchmark rules we took from LLMScanBench

Drafted by Claude. Approved for publication by Ayush-M99.

We planned two benchmarks: whether LLMs can write working Sigma detection rules, and how often they invent package names. Before running them we read LLMScanBench Q3 2026, Harness's benchmark of LLM vulnerability scanners. It changed our plan in five ways. The first run did not meet all of them, and the table at the end says which.

Run everything more than once

Harness scanned the same WebGoat code three times and got 16.2%, 19.7% and 35.5% recall. A single run could have reported any of those. We will run each model and prompt at least three times and report the spread.

Assume the model has seen the test

Harness points out that models may recognise well-known test applications, and that one benchmark ships its answer key in the repository. Public Sigma rules carry the same risk. We will keep rule titles out of prompts and report rules added after each model's knowledge cutoff separately.

Never report precision alone

Scanners there scored 85% to 100% precision while missing most vulnerabilities in WebGoat and Juice Shop. A Sigma rule that never fires also produces no false positives. We will report both numbers.

Measure cost and time

The two LLM scanners cost $21.79 to $133.58 per scan in Harness's tests. Accuracy alone will not tell a team whether a model is usable, so we will record both.

Think about who reads the output

This one is ours. The attack we are measuring works when someone registers a name that models keep inventing. The Mastra compromise shows how much damage one lookalike package can do. Publishing those names would hand attackers a list, so we will publish rates and redacted examples, and we will not register any name.

LLM-written Sigma rules against real attacks

Benchmark built and summarised by Claude. This post was checked against the repo's results files, and the benchmark was not rerun for it. Approved for publication by Ayush-M99. Code, prompts and results: sigma-llm-bench.

Each model got a plain-English description of 60 detections and wrote a Sigma rule for each. A rule counted as usable if it was valid Sigma, fired on the real recorded attack, and matched under 1% of about 33,000 benign Windows events. The human-written SigmaHQ rules were the reference, and all 405 SigmaHQ rules with regression data fired on their own attack events in the evaluator.

What stood out

  • Invented syntax. 81 of 238 rules were invalid, and 44 of those used a Sigma modifier that does not exist, such as |regex where the real one is |re.
  • Wrong, not noisy. Only 1 of 157 valid rules was noisy. But 77 valid rules missed their attack, and 75 of those had the wrong detection logic. A quiet rule can still detect nothing.
  • Hardest log sources. Registry rules were usable 44% of the time, against about 30% for process creation and PowerShell.

Limits of this test

  • One generation per rule at temperature 0.2, so these numbers carry no measure of spread.
  • Prompts included SigmaHQ titles and descriptions, and there is no holdout. Models may have seen these rules in training, so the scores may flatter them.
  • "Detects" means firing on one recorded execution. It does not cover variants of the attack.
  • The benign logs come from lab machines, with only 111 unique PowerShell script blocks. Enterprise false positive rates would likely be higher.
  • mistral-large-4 was excluded after answering only 6 of 60 tasks on the free tier.

How often LLMs invent packages

Benchmark built and summarised by Claude. This post was checked against the repo's results files, and the benchmark was not rerun for it. Approved for publication by Ayush-M99. Code and aggregate results: slopsquat-bench.

Eighty coding requests went to each model, half Python and half Node.js, half common tasks and half niche security or hardware tooling. Every package name in an install command was checked against PyPI or npm. Across 559 mentions, 30 did not exist: 5.4%.

Task typeNamesDo not existRate
Common, Python and Node.js30500.0%
Niche, Python12197.4%
Niche, Node.js1332115.8%

Rates by model ran from 2.6% (gpt-oss-20b) to 8.4% (nemotron-3.5-lightning-30b-a3b). Of 24 unique invented names, 5 came from two or more models independently. Those matter most, because one registered name would catch users of several assistants.

Limits of this test

  • One sample per task per model, so this does not show how persistent an invented name is.
  • "Exists on the registry" does not mean safe. Registration dates and maintainers were not checked.
  • Near-miss analysis of invented names is based on examples, not a measured rate.
  • mistral-large-4 was excluded after answering only 24 of 80 tasks.
